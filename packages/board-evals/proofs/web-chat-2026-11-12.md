# Web chat through the console proxy, on a real eve run (eve 1.0.0-rc.9)

Measured 2026-11-12 against eve 1.0.0-rc.9 with the repository's framework patch, by
`../scripts/web-chat-proof.mjs`, on branch `eve-1.0` at `6fc0095c` plus this change to the proof.
The same proof on eve 0.60.1 is `web-chat-2026-09-20.md`. Re-run it with

```sh
pnpm -C packages/board-evals run proof:web-chat
```

Docker running (one disposable `pgvector/pgvector:pg16` database). A real eve process (`eve build`
+ `eve start`), every `services/box/sql` file applied in number order, the console's real
`forwardChat` imported (not copied), eve's own `Client`, and the console's real member store and
grant store. Only the model is scripted (the package's own `mockModel`): no credential, no
gateway, no money. 16 s measured, about 40 s with the database start and the build.

## What changed in the proof, and which checks changed

The proof had been half moved to eve 1.0 (stream version 27 reading) but never run. Running it as
it was failed before the first item: `node` cannot load the console proxy any more, because the
proxy now imports agent-kit TypeScript through `.js` paths. Then the proxy's collaborators had
changed. The changes, all inside `packages/board-evals`:

- **Run with `tsx`** (`package.json`), as the member private-chat proof already is.
- **The proxy's checks are fed real rows, not a stub.** The proxy now asks the member store who is
  signed in (`signedInMember`, a real session token) and the grant store whether that member may use
  the agent, and it records each new conversation in `console_session_bindings`. The fixture
  therefore applies every box SQL file (not just the baseline), and seeds an organisation, an owner
  member with a session, the agent's definition row and the owner's adoption of the agent. The
  definition row is the one the agent itself records (`loadDefinition`, same hash): with any other
  hash the agent's first turn changes the definition, which bumps its access revision and retires
  every console conversation. That happened in the first port attempt and is correct product
  behaviour, not a fault.
- **A browser cookie jar.** On a successful create the proxy now sets the conversation's capability
  cookie, and refuses a continuation or a stream without it. The proof keeps a path-scoped jar and
  sends the cookie as a browser would; the small HTTP server in item 3 does the same for eve's
  `Client`, which keeps no cookies in Node.
- **Item 2c and the per-response check: "no `set-cookie` anywhere" became "no `set-cookie` except
  the proxy's own conversation cookie on a successful create".** That cookie is checked exactly:
  name `lares_chat_<session id>`, a 43-character value, `Path=/api/chat/<agent>/eve/v1/session/<id>`,
  `HttpOnly`, `SameSite=Lax`, `Secure`, and no password in it. Any other cookie, on any other
  response, still fails. This is the one check whose wording changed because the product changed.
- **Item 6b: an unknown agent now answers `403`, not `404`.** The proxy checks the member's access
  to the agent (`requireConsoleAgentUse`) before it looks at the registry. Zero upstream calls is
  still asserted. The registry's own `404` (and its `not-running` marker) is now asserted on a
  granted agent whose registry row is pending, so both refusals are covered.
- **Item 5 counts stored lines only.** eve 1.0 opens a held stream with a `$eve` heartbeat, a
  transport record sent the moment the connection opens. Counted, it made the "first line" arrive
  251 ms *before* the message was sent and failed the check. The thresholds (more than one line,
  more than 500 ms between first and last, first line after the send and more than 500 ms before
  the turn ends) are unchanged.
- **Item 7: the fixture's gated tool wraps its policy in `withCardTitle(always())`.** On eve 1.0 a
  card's title comes from the object form of a tool's `approval`, and every real gated tool is
  wrapped this way (`services/chief-of-staff/agent/tools/catalogue.ts`). With a bare `always()` the
  wire carried eve's default `Approve Gmail send?` and the item failed; that was the fixture, not the
  product.
- **Diagnostics only:** a refused stream open prints its status, and a failure inside the injected
  fetch is printed and fails the run (the proxy turns any such failure into its own `502`, which
  would otherwise read as a refusal). Sandbox containers labelled with this run's session ids are
  removed at the end.

## What an approval looks like on the wire now

The card is one fact on one stored line, then the turn pauses on the next:

```json
{ "type": "interaction.opened", "scope": { "turnId": "turn_0" },
  "data": { "interactionId": "<id>",
    "request": { "kind": "approval", "display": "confirmation", "allowFreeform": false,
      "options": [ { "id": "approve", "label": "Approve" }, { "id": "deny", "label": "Deny" } ],
      "prompt": "Send email to first@example.invalid and 1 more — \"The quarterly note\" (shortened)" },
    "subject": { "callId": "<tool call id>" } } }
```

followed by `turn.paused` (`awaiting: [{ interactionId }]`) and `delivery.settled` with outcome
`awaiting-input`. Compared with eve 0.60.1: the answer is `answers: [{ interactionId, optionId }]`,
the second option is `deny` (was `cancel`), and the card no longer carries the tool's input, only its
call id.

## What this does not prove

- The fixture's door is eve's HTTP door with the same auth chain every role uses (`localDev()` then
  Basic with realm `lares`, password read from a file), not a role's door. A role's door now also
  admits the console's member headers (`x-lares-member-id`, `x-lares-admission`,
  `x-lares-purpose`); this fixture ignores them. A role's door with the real proxy is what the member
  private-chat proof covers (`member-private-chat-2026-11-11.md`).
- No approval is answered here. Answering a card in web chat on eve 1.0 is not proved by this file;
  see `web-chat-approval-2026-11-12.md`.
- No vault capsule, model-purpose signing or budget: none is configured in this fixture, so the
  proxy skips them.
