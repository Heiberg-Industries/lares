# Web chat, proved on a real eve run — 2026-09-20 (W8B-s4)

`services/console/lib/chat-proxy.ts` and `services/console/components/Chat.tsx` were built from unit
tests and from reading eve 0.60.1's compiled client. Nobody had watched either carry a turn. This is
that observation.

```sh
pnpm -C packages/board-evals run proof:web-chat
```

**Roughly 35 seconds end to end** on an idle machine (a disposable `postgres:16-alpine` container
comes up, `eve build` takes ~4 s, the door is answering ~1.5 s later, and the measured part of the
run takes ~10 s). Docker must be running. No model credential, no gateway, no money: the package's
own `mockModel` is scripted. Nothing outside `packages/board-evals` changes, and the fixture itself
is a disposable copy — the door, the instrumentation hook and the three tool files this proof needs
are written into that copy, never into the source tree.

## What was real

- a real eve 0.60.1 process — `eve build`, then `eve start --host 127.0.0.1 --port <free>`;
- its real HTTP door, carrying the same policy every role ships (W8B-s1):
  `[localDev(), withAuthChallenges(basicFromSecretFile, [{ scheme: "Basic", parameters: { realm: "lares" } }])]`,
  reading a real route-password **file** on the first request, never at import;
- a real Postgres, with `039/042/044/045` applied and a registry row for the agent;
- the real `forwardChat`, **imported, not copied**;
- eve's own browser `Client` from `eve/client` — the transport `useEveAgent` wraps.

**How a `.ts` module is imported from an `.mjs` proof:** it just is. Node 24 strips the types off a
`.ts` file on import with no flag and no build step, so the script's import is the plain relative
specifier `../../../services/console/lib/chat-proxy.ts`. There is no second copy of the proxy
anywhere in this proof and nothing to drift.

**How the fixture is bound.** `forwardChat` refuses a loopback address on purpose — the agent must be
a ready, runtime-controlled row on a private IPv4 — so the proof injects `deps.fetch`, asserts that
the URL the proxy **would** have called is exactly `http://10.0.0.7:3000/<path>` (the address the
console's own registry query returned, never one the request chose) with
`Authorization: Basic base64("eve:<password>")` and `redirect: "error"`, and only then re-issues that
same request against the real loopback port. The injected fetch is also the request **counter** that
the three negative cases assert is zero.

## Three things the run established that reading the code did not

1. **`POST eve/v1/session` answers `202`, not `200`.** Anything asserting `status === 200` on a
   create or a send is wrong; use `response.ok`.
2. **`includeTailIndex=1` turns a read into a bounded snapshot.** Asked for on a *live* turn, the
   server serves what exists and closes, one small batch at a time. eve's own client asks for it
   only on a bounded read (`follow: false`). A follow reader must omit it.
3. **A reader that attaches after the turn has begun is served a batch and the connection closes.**
   The stream has to be opened *first* and held for a single connection to span a turn. That is also
   why item 5 opens before it sends: a reader that attaches late measures the race, not the proxy.

## Item 7 — what an approval looks like ON THE WIRE (for W8B-s5)

The stream the browser receives is NDJSON, one event per line. A parked approval is **two** events,
both carrying the same `meta.deliveryIds`, in this order.

The card itself, verbatim:

```json
{
  "data": {
    "requests": [
      {
        "action": {
          "callId": "mock-tool-call-1-0-1",
          "input": {
            "from": "agent@example.invalid",
            "to": ["first@example.invalid", "second@example.invalid"],
            "subject": "The quarterly note",
            "bodyText": "Here is the note you asked for.\nIt is two lines long."
          },
          "kind": "tool-call",
          "toolName": "gmail_send"
        },
        "allowFreeform": false,
        "display": "confirmation",
        "kind": "tool-approval",
        "options": [
          { "id": "approve", "label": "Approve" },
          { "id": "cancel", "label": "Cancel" }
        ],
        "prompt": "Send email to first@example.invalid and 1 more — \"The quarterly note\"",
        "requestId": "aitxt-IkcQJPCt71XN1iSZUc7c2TLy"
      }
    ],
    "sequence": 0,
    "stepIndex": 0,
    "turnId": "turn_0"
  },
  "type": "input.requested",
  "meta": {
    "at": "2026-09-20T05:30:13.158Z",
    "id": "evt_01M2YMP8S6VN7W60J2SKNDBZ2Q",
    "deliveryIds": ["918cbf91-2f2a-4578-84ec-18c1a72906b2"]
  }

```

and immediately after it, the event that tells the browser the turn has stopped and is waiting:

```json
{
  "data": {
    "continuationToken": "wrun_01M2YMP8R2YRSHJNCGGBRQ884Q",
    "wait": "next-user-message"
  },
  "type": "session.waiting",
  "meta": {
    "at": "2026-09-20T05:30:13.158Z",
    "id": "evt_01M2YMP8S6VN7W60J2SKNDBZ2S",
    "deliveryIds": ["918cbf91-2f2a-4578-84ec-18c1a72906b2"]
  }
}
```

**The fields W8B-s5 has to build on**, in the order a renderer needs them:

- `type: "input.requested"` — the only event type that carries a card.
- `data.requests[]` — an ARRAY. A turn can park on more than one.
- `requestId` — what `agent.respond([{ requestId, optionId }])` must send back. It is eve's
  `approvalId`, not the tool call id.
- `kind: "tool-approval"` — the discriminator. The other kind on this route is `"question"`.
- `options: [{id:"approve",label:"Approve"},{id:"cancel",label:"Cancel"}]` — the two buttons, with
  eve's own ids. `display: "confirmation"`, `allowFreeform: false`.
- `prompt` — the **one-line title** only, and it is already the Lares one: this run registered the
  real `registerApprovalSummary()` hook and the wire carried
  `Send email to first@example.invalid and 1 more — "The quarterly note"` rather than eve's default
  `Approve tool call: gmail_send`.
- `action.toolName`, `action.callId`, `action.input` — the raw, schema-parsed tool input.

**The card's DETAILS text is NOT on the wire — only the one-line title.** This is the single most
important finding for W8B-s5, and it is a property of where the eve patch injects each half:
`__eveApprovalSummary` is called in `dist/src/harness/input-extraction.js`, which is what builds the
`prompt` every channel and the HTTP stream see; `__eveApprovalDetails` is called only inside the
**Slack** and **Telegram** renderers (`public/channels/slack/hitl.js`, `public/channels/telegram/hitl.js`).
The HTTP door has no such renderer. The proof asserts this directly: no `*To:*` block appears
anywhere in the stream, although `detailsForApproval("gmail_send", …)` returns one for this input.

So a web-chat card that shows only `prompt` shows the owner strictly less than the Slack or Telegram
card does — for a mail send, every recipient and the draft itself would be missing. W8B-s5 has two
honest ways to close that, and should pick one deliberately:

- render `detailsForApproval(action.toolName, action.input)` **in the console**, from `action.input`,
  which is on the wire in full; or
- have the console render `action.input` itself.

The first reuses the text the owner already sees elsewhere and keeps one wording; the second needs no
new console dependency on `@lares/agent-kit`. Either way, the input is there — nothing needs to be
added to the proxy's allow-lists.

## Not touched, noticed

- `x-eve-stream-tail-index` is only emitted when `includeTailIndex=1` is asked for; the proxy already
  allows it through. Nothing to change.
- The negative case `eve/v1/session/<id>/subagents/<callId>/<childId>/stream` is a real eve route and
  is correctly **off** the console's allow-list, so a subagent's stream is not relayed to the browser.
  If web chat is ever meant to show subagent activity, that is a deliberate decision, not an oversight.
