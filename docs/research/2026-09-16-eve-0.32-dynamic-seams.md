## How the tool set and the system prompt were read

The plan's brief guessed at `turn.tools` and `turn.instructions`. **Neither exists.** eve 0.32's eval
harness exposes exactly this on an immutable turn (`EveEvalTurn`,
`eve/dist/src/evals/types.d.ts`): `data`, `events`, `inputRequests`, `message`, `sessionId`,
`status`, `toolCalls`, `requireToolCall()`, `expectOk()`. There is no accessor for the model's tool
set and none for the resolved instructions.

So the measurement goes through the model instead. `mockModel`'s request view
(`MockModelRequest`, `eve/dist/src/evals/mock-model.d.ts`) carries `tools` (name + description) and
`messages` (including the `system` role) — the real thing eve handed the model on that call, not a
reconstruction. `packages/board-evals/agent/agent.ts` answers a small set of `seam …` messages by
reporting them back as its reply, and the eval reads `turn.message`. This is a **better** route than
the brief's: it observes what the model was actually given, one layer below any harness bookkeeping.

## Q1 — a `session.started` map produces exactly those tools, and overrides an authored file

Granted `["cat_alpha", "atlas_write"]`. `agent/tools/atlas_write.ts` is an authored tool that still
exists on disk (that is the point of the question), and `agent/tools/catalogue.ts` emits its own
`atlas_write` from the same session.

```text
[seams] Q1/Q2 tool set: TOOLS agent ask_question atlas_write bash cat_alpha glob gmail_send grep
        load_skill probe__probe_live_tool read_file seam_language todo web_fetch write_file
[seams] Q1 atlas_write: DESCRIBE atlas_write count=1 Catalogue's own atlas_write.
[seams] Q1a granted catalogue tool present: YES
[seams] Q1b authored tool overridden, not duplicated: YES — DESCRIBE atlas_write count=1 Catalogue's own atlas_write.
[seams] Q1c the catalogue's executor answers atlas_write: YES — atlas_write output = {"from":"catalogue","tool":"atlas_write"}
```

Three things this proves, in order of how much they matter:

1. `atlas_write` appears **once**, not twice (`count=1`).
2. The description the model sees is the **catalogue's** (`Catalogue's own atlas_write.`), not the
   authored file's (`Write a note (fixture).`). The override is on the definition, not a merge.
3. The override is **behavioural**: calling it runs the catalogue's executor
   (`{"from":"catalogue"}`), so the authored file's `boardApproval(...)` no longer applies. A
   catalogue entry replaces an authored tool *completely*, approval included — worth knowing when
   Task 7 moves real tools into the catalogue.

Everything else in the list is eve's default harness (`agent`, `bash`, `read_file`, …) plus the
fixture's other authored tools. The resolver contributes exactly its map and nothing more.

**Consequence for the plan: the catalogue can be ONE file.** The 100-plus-file fallback
(`agent/tools/<t>.ts` per tool, each wrapping its own `defineDynamic`) is not needed.

## Q3 — a prefixed key from the agent's own catalogue, over a disabled extension slot

This is D10. The fixture mounts a real extension (see [The probe extension](#the-probe-extension))
whose namespace is `probe`. The mount disables the extension's own
`probe_extension_tool` with `disableTool()`, and the agent's catalogue emits
`probe__probe_extension_tool` from `agent/tools/catalogue.ts`.

```text
[seams] Q3 tool set: TOOLS agent ask_question atlas_write bash glob gmail_send grep load_skill
        probe__probe_extension_tool probe__probe_live_tool read_file seam_language todo web_fetch write_file
[seams] Q3a the probe mount is live (control): YES — probe__probe_live_tool present
[seams] Q3b the prefixed catalogue key appears exactly once: YES — DESCRIBE probe__probe_extension_tool
        count=1 Catalogue's copy of the probe extension tool.
[seams] Q3c the catalogue's copy answers, not the extension's: YES —
        probe__probe_extension_tool output = {"from":"catalogue","tool":"probe_extension_tool"}
```

`probe__probe_live_tool` is the control: an extension tool with no override, present in the same
list. It proves the mount is live and `probe__` really is that extension's namespace, so the
catalogue's key is a genuine collision test rather than a prefix nobody owns.

The run completed with no throw and no diagnostic. **D10 stands: the 12 kit tools can be resolved
per definition rather than per pool, and the build-time `resolveExtensionTool` seam can go.** No
CHANGELOG gap note is needed.

One caveat worth carrying into Task 7. eve's own extensions documentation states:

> The `crm__` prefix is reserved for this directory mount. A consumer cannot override the extension
> from `agent/tools/`, `agent/connections/`, or another agent-root slot.

That sentence is about **authored** agent-root files. It does **not** hold for a dynamic resolver:
measured here, a `defineDynamic` map key under a mounted extension's prefix is accepted. This is
undocumented behaviour we now depend on, so this eval is the regression guard — if a future eve
closes the gap, `seams.eval.ts` fails loudly rather than the fleet losing 12 tools quietly.

## Q4 — session state reaches the next turn's instruction resolver, and no further

`agent/tools/seam_language.ts` writes `lib/seam-state.ts`'s `defineState` slot.
`agent/instructions/seam_lang.ts` is a `turn.started` `defineDynamic` that reads the same slot and
emits `SEAM_LANG=<value>` into the system prompt.

```text
[seams] Q4 set: RESULT seam_language {"lang":"no"}
[seams] Q4 system prompt on the NEXT turn: SYSTEM Instructions (instructions)
        A test agent for the permissions board.
        …
        SEAM_LANG=no
[seams] Q4a the next turn's instruction resolver sees the stored value: YES
[seams] Q4b the value survives the turn boundary: YES — seam_language output = {"lang":"no"}
[seams] Q4 other session system prompt: … SEAM_LANG=en
[seams] Q4c the value does not leak to another session: YES — other session: {"lang":"en"}, … SEAM_LANG=en
```

Turn 1 stores `no`. Turn 2's instruction resolver — a different bundle from the tool — reads `no`
and it lands in the system prompt eve assembled for that call. A second session started moments
later reads the initial `en`, in both the tool and the resolver.

Two mechanics worth recording:

- **`defineState` is safe across eve's bundle split.** `lib/file-board.ts`'s header documents the
  trap: eve compiles `instrumentation.ts` and `agent.ts` + tools into separate bundles, each with its
  own copy of a shared module, so a module-level variable set in one is invisible to the other.
  `defineState` is keyed by its **name** string, not by the module object, so it does not have that
  problem. A tool and an instructions resolver in different bundles read the same slot.
- **State access works inside a dynamic instructions resolver.** eve's docs only hint at this
  ("Durable per-session memory for resolvers to read"); it is now measured.

**Consequence: no `agent_session_language (session_id, lang)` table.** The language switch can live
in eve session state.

## Q5 — a dynamic model, and the one constraint on it

`agent/agent.ts` now carries `model: defineDynamic({ fallback, events: { "session.started",
"step.started" } })`. It **compiles**:

```text
$ pnpm exec eve build      # in packages/board-evals
[nitro] ✔ Server built in 733ms
[BUILD] built output at /Users/operator/Developer/lares/packages/board-evals/.output
eve build exit=0
```

and the fallback still anchors the build-time window — `modelContextWindowTokens: 2e5` is in the
compiled server bundle, the `200_000` declared beside the dynamic model. No compaction complaint.

At runtime the scope matters, and this is the constraint:

```text
[eve:dynamic-models] Dynamic model resolver (session.started) returned a provider object, but
session- and turn-scoped model selections must be serializable. Return a model id string for this
scope, or use "step.started".
[seams] Q5a session.started refuses a provider object and degrades to the fallback: YES
        — reply = [waiting] TOOLS agent ask_question atlas_write …

[eve:harness.tool-loop] AI Gateway authentication failed: AI Gateway received no credentials.
[seams] Q5b session.started accepts a model ID string and routes the turn to it: YES
        — reply = [failed] <no message>

[seams] Q5c step.started may return a provider object: YES — reply = [waiting] ALT-MODEL:seam tools
[seams] Q5d a null selection falls back to the compiled model: YES — reply = [waiting] TOOLS agent …
```

Read in order:

- **Q5a** — a **provider object** (an AI SDK `LanguageModel`) returned at `session.started` is
  refused with the message above, and eve degrades cleanly to the compiled fallback. Not a defect:
  session- and turn-scoped selections are stored in durable workflow state and must be serializable.
- **Q5b** — a **model ID string** is accepted and routed. The fixture returned
  `"board-evals/alternate"`; the turn failed *inside the AI Gateway call* for want of credentials,
  which is the proof: eve used the dynamically selected model, not the compiled fallback (the
  fallback is a local mock and cannot fail that way). The eval asserts on that exact signature —
  `[failed]` + `MODEL_CALL_FAILED` + `AI Gateway`, and neither model's reply — because "the answer
  was not the fallback's" would also be satisfied by a resolver crash, a schema error or a timeout,
  and the whole point of this eval is to fail when the seam stops working *for any reason*. For a
  real Lares agent, which already routes every model id through the LiteLLM gateway as a purpose
  alias (`lares-brain`, `heiberg-gate`), a string is what a definition would return anyway.
- **Q5c** — `step.started` accepts a provider object and the alternate model served the turn. Not
  what the plan wants (prompt caches are per model; switching per step re-ingests the conversation
  at uncached prices), but it is the scope to reach for if an object is ever unavoidable.
- **Q5d** — `null` leaves the scope unset and the compiled fallback serves, so every other eval in
  this package is unaffected by the dynamic model being present.

**Verdict: YES**, and the Q5 change is **kept** in the fixture (Task 18 can build on it).

**Task 5 must honour this:** a definition's model is a **model ID string** resolved through the
gateway, never a constructed provider object. `modelContextWindowTokens` is **not inherited** by a
runtime selection — eve's `agent-config.md` says to pass
`{ model, modelContextWindowTokens }` as a selection object when the selected model's window differs
from the fallback's. A definition that can select models with different windows must carry the
window with the selection.

## Q6 — a `null` dynamic override does not remove a static extension tool (LAR-5)

Not a fixture question: LAR-5's ticket, read against eve 0.32's own compiled source rather than
against a probe eval, because the bug is in the compiler's merge step, not in anything an eval's
mock model could distinguish by asking it a question at runtime.

`services/chief-of-staff/agent/extensions/agent-kit/tools/market_edge.ts` used to be a
`defineDynamic` whose `session.started` handler resolved the mounted definition and returned
`null` when the agent had not declared the `market-edge` skill — the same shape Q1 and Q3 measured
working correctly for a **resolver-emitted** tool. The difference is where the *other* copy of the
tool comes from. `packages/agent-kit/extension/tools/market_edge.ts` is the kit's own contribution,
and it is a plain `defineTool`, a **static** tool, not a dynamic one — unlike `signals_recent` or
`transit_plan`, nothing in the kit extension resolves `market_edge` dynamically on its own.

`eve/dist/src/compiler/normalize-extension.js` merges an override's contributions with the
extension's own in two separate lists that never cross-reference each other:

```js
function mergeContributions(e,t){return{
  tools: dedupeBy([...e.tools,...t.tools], e=>e.name),
  dynamicTools: dedupeBy([...e.dynamicTools,...t.dynamicTools], e=>e.slug),
  // …
}}
```

The override file compiles to a **dynamic-tool** contribution (slug `agent-kit__market_edge`), and
the extension's own `market_edge.ts` compiles to a **static-tool** contribution (name
`agent-kit__market_edge`). `mergeContributions` dedupes `tools` against `tools` and `dynamicTools`
against `dynamicTools` — never `tools` against `dynamicTools`. So the merged manifest ends up with
BOTH: the extension's static tool, unconditionally, AND the override's dynamic resolver.

`applyOverrideDisables` is the only step that ever removes a tool the extension contributed, and it
only acts on names an override's `disabledToolTargets` actually lists — populated exclusively by a
**module-scope, unconditional** `disableTool()` call compiled at build time (`compileToolEntry`
classifies the override file's *default export shape*, not what a resolver returns at runtime).
A `defineDynamic` resolver returning `null` from inside a `session.started` handler is invisible to
this step entirely — it is a runtime value, produced long after the build-time merge already
decided which tools exist. So the static tool from `packages/agent-kit/extension/tools/
market_edge.ts` stays in the compiled `tools` list on every build, and the model gets it on every
session, whatever the dynamic resolver would have returned.

**Consequence:** the only way to actually remove a kit-contributed tool per session is the pattern
Task 9 already used for the other twelve `agent-kit__*` tools — turn the override slot into an
unconditional, build-time `disableTool()` (which DOES get compiled as a static discriminator
`applyOverrideDisables` can see and file into `disabledToolTargets`), and reach the tool instead
through the service's own `agent/tools/catalogue.ts` resolver, which is checked at RUNTIME by
`grantedToolNames` — no merge-time deduplication involved, because it never emits a name it isn't
handing over. LAR-5-s2 moves `market_edge` onto that path.

## The probe extension

Q3 needs a real mounted extension namespace, and the brief's shape for it does not compile. eve
resolves a mount's default export back to a **package**: `locateExtensionMountPackage`
(`eve/dist/src/discover/extensions.js`) requires a directory containing a `package.json` that
declares `eve.extension.dist`, and fails with `discover/extension-mount-unresolved` otherwise. An
inline `defineExtension()` in the mount file is not a package and is rejected.

So `packages/board-evals/probe-extension/` is a real, minimal extension package, mounted by the
**relative specifier** `"../../../probe-extension"` — eve's `resolvePackageRoot` accepts a relative
path to a package root. That keeps the whole fixture inside `packages/board-evals` with no workspace
member, no dependency on `@lares/agent-kit`'s extension and no lockfile change. Three details cost
time and are worth writing down:

1. **Declare `eve` as a peer dependency.** Without it the extension build fails with
   `Package "eve/tools" is not declared by the extension. Add "eve" to dependencies,
   optionalDependencies, or peerDependencies.` The check is on the *declaration*, not the install.
2. **Add `"main"`.** `eve extension build` writes an `exports` map into the package's `package.json`
   by itself, but `exports` only applies to bare specifiers; a **relative** directory import needs
   `main`. Without it: `Could not resolve '../../../probe-extension'`.
3. **It is not `@lares/agent-kit`.** `eve dev` rebuilds every source-backed extension a mounted agent
   reaches, so mounting agent-kit here would rewrite `packages/agent-kit/dist/extension` underneath
   whatever session is building `services/chief-of-staff`. A local package touches nothing else.

`probe-extension/dist/` is gitignored and rebuilt on demand, so a fresh clone is fine.

## What was skipped, and why

- **The `brain` grant in `agent.json`.** A deliberate substitution, not an oversight: the brief added
  the grant so the probe had a second capability to switch on and off, and the fixture switches
  capabilities through the `SEAM_GRANTS` file instead — one control file the eval rewrites between
  sessions, readable by the tool catalogue *and* the model resolver. Q1–Q3 are answered without it,
  so `agent.json` is untouched and the fixture's capability set still matches what `board.eval.ts`
  asserts on.
- **`maxConcurrency: 1` was added** to `evals/evals.config.ts`, and it is load-bearing.
  `board.eval.ts` and `seams.eval.ts` drive the same agent process, and `seams.eval.ts` grants
  `atlas_write` — which overrides the authored tool `board.eval.ts` asserts on. At eve's default
  concurrency of 8 the two race. Serialized, and with `seams.eval.ts` clearing the grants in a
  `finally`, they pass in either order.

## Task17 — disabled door and lazy credentials

Code read: `services/chief-of-staff/agent/channels/slack.ts:42–52` reads a secret only inside `readSecret`; `:64–74` exposes bot token as an async function and signing secret as a getter. The actual file is under `agent/channels`, not the task sketch's `lib/…` path. Installed eve `dist/src/public/channels/slack/slackChannel.js` calls verification before dispatch and before built-in interactions; its async `webhookVerifier(Request, rawBody)` seam permits a managed current-authority check without weakening platform verification. Telegram's documented async webhook-secret function checks managed authority before returning the configured secret; claim handlers run only after eve verifies the header.

The companion `packages/board-evals/evals/doors.eval.ts` is a real mock-runtime eval with an authored disabled Telegram adapter and no token, not a fixture-only assertion about a URL. Its turn completes and its instrumented credential/outbound paths remain untouched. Runtime claim proof and manual live acceptance limits are recorded in `2026-09-16-door-installation.md`.
