# Reading eve's `@workflow/world-postgres` pairing when eve states no range

**Problem.** Every eve bump moves `@workflow/world-postgres` too (ADR-0021 decision 6), but eve's own
`package.json` cannot tell you which version. eve vendors the whole `@workflow/*` tree into its own
`dist/` and imports it through `#compiled/` subpath aliases; the app's `@workflow/world-postgres` is a
separate, parallel package loaded by name at runtime. eve's dependency list is two entries —
`"dependencies": { "nitro": "3.0.260903-beta", "undici": "8.9.0" }` (`v060/package/package.json`) —
neither of them `@workflow/*`. There is no manifest field that says "use world-postgres beta.N".

**Method — re-derive this on every bump, do not carry the number forward:**

1. Unpack the target eve tarball (see the two commands below).
2. Read the version eve actually vendors for `@workflow/world-local`:
   ```bash
   grep -rhoE '5\.0\.0-beta\.[0-9]+' <unpacked>/package/dist/src/compiled/@workflow/world-local/ | sort -u
   ```
   For eve 0.60.1 this returns exactly `5.0.0-beta.44`, one value, from every minified file in that
   directory.
3. Read the dependency table of every published `@workflow/world-postgres` and find the one whose own
   `@workflow/world-local` pin equals what step 2 returned:
   ```bash
   npm view @workflow/world-postgres versions --json | tail -5
   npm view @workflow/world-postgres@<candidate> dependencies --json
   ```
   For eve 0.60.1: `world-postgres@5.0.0-beta.32` (the version pinned in this repo today) wants
   `world-local@beta.34` — no match. `beta.41` wants `beta.43` — no match. **`beta.42` wants
   `beta.44`** — the only match among the five most recent published versions
   (`beta.41`..`beta.44`, plus `beta.32`). `beta.42`'s full dependency set, read the same way:
   `zod: "~4.5.4"`, `pg: "8.20.0"`, `drizzle-orm: "0.45.2"`, `graphile-worker: "0.16.6"`,
   `@workflow/world: "5.0.0-beta.35"`.

**This is a strong signal, not a proof.** eve vendors `world-local` and the app supplies
`world-postgres`; the two packages only have to agree on the wire protocol between
`@workflow/world` implementations, and neither package publishes a version range for that protocol.
Treat the vendored-version match as the *starting* pin, and confirm it with a real restart —
this wave's W2-s13 restart proof is what actually decides whether beta.42 works, never the manifest
match alone.

**Re-creating the evidence** (disposable scratch directory, never the repo):
```bash
D=<scratch-dir>/eve-060
mkdir -p "$D"/v032 "$D"/v060
( cd "$D/v032" && npm pack eve@0.32.0 && tar xzf eve-0.32.0.tgz )
( cd "$D/v060" && npm pack eve@0.60.1 && tar xzf eve-0.60.1.tgz )
```

**Other version facts confirmed the same way, for this bump (eve 0.60.1):**

- `npm view eve@0.60.1 peerDependencies --json` → `ai: "^7.0.105"` (repo pins `^7.0.58`),
  `dd-trace: "^6.13.0"` (new, marked `optional: true` in `peerDependenciesMeta` — nothing to
  install; do not add a Datadog client to satisfy the warning), plus `just-bash`, `braintrust`,
  `microsandbox`, `@opentelemetry/api`, all optional.
- `npm view eve@0.60.1 engines --json` → `{"node": ">=24"}`, and the same value is in
  `<unpacked>/package/package.json` for *both* 0.32.0 (line 381-383 of the pack) and 0.60.1
  (line 564-566) — the floor did not move with this bump, the root `package.json`'s `>=22` was
  already wrong.
- `zod` newest release satisfying world-postgres beta.42's `~4.5.4` is `4.5.4` itself
  (`npm view zod versions --json`; `4.5.5` does not exist, the next release is `4.6.0`, which the
  tilde range excludes).

**Why this matters for the next monthly bump:** the manifest will keep saying nothing. Whoever reads
this next re-runs steps 1-3 against the new tarball; the vendored `world-local` version is very
likely to change again, and the matching `world-postgres` beta may not be adjacent to today's.

**The patch key is version-pinned on purpose, and the bump must move it.** Root `package.json`
reads `"patchedDependencies": { "eve@0.60.1": "patches/eve.patch" }`, not the bare `"eve"`, and the
next eve version has to change that key in the same commit that changes the version. Measured on
pnpm 9.15.0: with a **bare** key, a hunk that no longer applies is a `WARN` and `pnpm install`
exits **0**, having applied the hunks up to the failure and shipped a half-patched eve (6 of our 9
landed in the test — the three Telegram ones, including the approval-card detail rendering, silently
did not). With the **version-pinned** key the same patch is `ERR_PNPM_PATCH_FAILED`, exit 1; and
once eve moves off the pinned version the install stops before that, with
`ERR_PNPM_PATCH_NOT_APPLIED` (exit 1), or `ERR_PNPM_LOCKFILE_CONFIG_MISMATCH` (exit 1) under
`--frozen-lockfile`, which is what every image build and CI job uses. A loud stop at the bump is
worth more than the small chore, because the hunks this patch carries sit in the approval path: a
silently missing one means a person clicking "approve" authorised something other than what they
read.

## Moving an existing installation's workflow tables to the new shape (beta.32 → beta.42)

**The problem.** `services/{chief-of-staff,creative}/sql/001-eve-workflow.sql` is regenerated whole
on every `@workflow/world-postgres` bump — it is "the full schema, today", not a migration. A brand
new installation just applies the current file and is fine. An installation that is already
running has real rows in `workflow.workflow_events` (pending approvals, session history) sitting
under the OLD shape, and applying the regenerated file straight over it fails with:

```
ERROR: multiple primary keys for table "workflow_events" are not allowed
```

**The fix is one extra file, run once, before the regenerated one.** Each service now carries a
companion upgrade file next to its `001-eve-workflow.sql`:
`services/chief-of-staff/sql/006-eve-workflow-beta32-to-beta42-upgrade.sql` and
`services/creative/sql/002-eve-workflow-beta32-to-beta42-upgrade.sql` (same content in both — each
service's workflow tables live in their own database, per the standing "its own workflow database,
always" rule). It is safe to run more than once, and safe on a database that never had the old
shape at all — see the file's own header and `services/chief-of-staff/tests/eve-workflow-upgrade.test.ts`
for the proof.

**The exact order, for each affected role (chief-of-staff, creative), at night, one at a time:**

1. **Back up that role's workflow database.** The usual box backup covers this if it snapshots the
   whole Postgres instance; if the role's workflow tables live in a separate database, take a
   separate dump of it (`pg_dump` on just that database). Success looks like: a backup file exists,
   dated just before this maintenance window. Going back from here, before step 2, means nothing —
   nothing has changed yet.
2. **Stop that role's agent (the eve-saga process/container for that role).** This is the thing
   reading and writing `workflow.workflow_events`; it must not be running while the schema
   underneath it changes. Success looks like: the process/container is confirmed stopped (not just
   "restarting"). Going back from here means starting it again — nothing on disk has changed yet.
3. **Apply the upgrade file** (e.g. `psql <that database's connection string> -f services/chief-of-staff/sql/006-eve-workflow-beta32-to-beta42-upgrade.sql`,
   or the equivalent for creative). Success looks like: the command exits without error. It prints
   nothing alarming — a `NOTICE` about a missing index is expected and harmless on a database that
   never had the old shape. If it fails, nothing has been changed (the whole file is one
   transaction) — go back by doing nothing further, leaving the agent stopped, and investigating
   before retrying.
4. **Apply the regenerated schema file** (`services/chief-of-staff/sql/001-eve-workflow.sql`, or
   creative's). Success looks like: the command exits without error. This is the same file a fresh
   install would apply — after step 3, it always finds every constraint it expects already in
   place or safely re-creatable.
5. **Start that role's agent again.** Success looks like: the process/container comes up clean and
   a real turn (or the box's own health check) completes normally. Going back from here — if
   something is wrong with the new schema itself, not just this rollout — means restoring the
   database from the step 1 backup and rolling the role's image back to the previous version, per
   the standing rollback discipline (previous image digest + restore); this upgrade adds no new
   rollback mechanism beyond that.

Repeat steps 1-5 for the next affected role. There is no reason both roles must be upgraded in the
same maintenance window, since each keeps its own workflow database — but neither should be left
half-upgraded (steps 3 and 4 not both done) for longer than necessary, since the regenerated file,
not the upgrade file, is what actually adds the new `workflow.workflow_event_slots` table the new
eve version's code expects to find.

**What this does NOT change.** No row in `workflow.workflow_events`, or anywhere else, is dropped
or rewritten — only two schema objects move (the primary key is renamed and widened from `(id)` to
`(run_id, id)`; one now-redundant index is dropped). `@workflow/world-postgres` never runs its own
migrations at boot — only its `bootstrap` CLI does, and nobody runs that against a live box (see
`services/box/lib/migration-runner.ts`'s comments and `001-eve-workflow.sql`'s own header) — so
this step really does have to be done by hand, once, exactly as above.

## What the restart proof showed about the world pairing (W2-s13)

`packages/board-evals/scripts/restart-probe.sh` is the deciding evidence for **Owner decision 2**
(whether `@workflow/world-postgres@5.0.0-beta.42` is the right pairing for eve 0.60.1, per the
"strong signal, not a proof" method above). It PASSED three of five times run on this branch
tonight — `RESTART PROOF PASS: authored control + definition catalogue.` — with a genuine process
boundary each time (`first.pid !== second.pid`), a card left `input-required` across it, exactly
one execution of the approved effect, and three repeated mock proposals cancelled with zero side
effects. **beta.42 is confirmed; there was no need to try beta.43 or beta.44.**

Two of the five runs were NOT clean, and they failed two DIFFERENT ways:
1. The very first invocation after `probe-extension/dist` was rebuilt from nothing (see this
   branch's build-process fix) failed a `--resume approve` call with `The session is no longer
   active.` (exit 1, no timeout — the error came back fast).
2. A later run failed before the app even started invoking, with a raw Docker error from
   testcontainers: `no such container` (statusCode 404) — the ephemeral Postgres container (or its
   Ryuk reaper) disappeared out from under the harness.
Both times, an immediate retry passed cleanly. `docker ps -a` at the time of failure #2 showed
OTHER projects' Postgres test containers in `Created` state on this same machine — this looks like
Docker contention with a concurrent session on the same Mac (the standing "check the machine
first" rule exists for exactly this reason), not a defect in the eve 0.60.1 / beta.42 pairing.
Neither failure has the LAR-73 signature (that one is a 120-second `subprocess` timeout in the
*keeper* image probe; both of these were fast, explicit errors in *board-evals'* own restart proof,
a different probe entirely, and neither timed out). Recorded here rather than quietly retried away
— if failures like these start recurring even when nothing else is competing for Docker, that is
worth its own investigation.

`services/keeper/tests/conversation-runtime.probe.mts` also passed (real `eve build` + `eve
start`, disposable Postgres): the pinned model alias survives a mid-session definition edit, a new
session reads the edited model, and `attachSession(id).reset()` really ends a session (a further
`send` on the old id is rejected). This is a session-level reset proof, not a process-restart proof
— `restart-probe.sh` is the one that exercises an actual OS process boundary.

**The three spec §9 questions, answered against the real install (not assumed):**

1. **Does `sandbox-shutdown-plugin.js` still call `process.exit(143)` ahead of graphile-worker's
   graceful shutdown?** Yes, unchanged. `eve/dist/src/internal/nitro/host/sandbox-shutdown-plugin.js`
   registers its own `SIGTERM`/`SIGINT` handlers, races its sandbox-handle shutdown against a 15s
   timeout, then calls `process.exit(143)` for `SIGTERM` (130 for `SIGINT`) in a `.finally()`. This
   is eve's own shutdown path, independent of and not sequenced against graphile-worker's separate
   `SIGTERM` listener — the same architecture as on 0.32, not something this bump changed.
2. **Does `WORKFLOW_INLINE_OWNERSHIP_LEASE_SECONDS` still exist, and what is its default?** Yes —
   but not where the spec's suggested grep looks. It is not part of the app-level
   `@workflow/world-postgres` package at all; it is a constant in **eve's own vendored**
   `@workflow/core` runtime (`eve/dist/src/compiled/@workflow/core/runtime/constants.d.ts`):
   `INLINE_OWNERSHIP_LEASE_SECONDS = 860`, clamped to a max of `900` via
   `MAX_INLINE_OWNERSHIP_LEASE_SECONDS`. (Searching only
   `services/chief-of-staff/node_modules/@workflow/` finds nothing — that directory holds the
   separate app-level `world-postgres` package, not eve's vendored `world-local`/`core`.) This lease
   governs which process may run a step's work inline, a different mechanism from graphile-worker's
   job lock in point 3 below; nothing here suggests it moved between beta.32 and beta.42.
3. **Does the graphile-worker job-lock expiry (four hours on beta.32) still hold on beta.42?** Yes,
   unchanged. `world-postgres@5.0.0-beta.42` pins `graphile-worker@0.16.6`, and that version's own
   SQL (`get_job()`, `resetLockedAt()`) hard-codes `interval '4 hours'` for both the default
   `job_expiry` argument and the stale-lock sweep — no environment override, no config field, same
   as beta.32.

**LAR-73, the deliverable this slice owes it (not fixed here — that is other work's job):** no
detectable change. The new eve 0.60.1 / world-postgres beta.42 pairing keeps graphile-worker's job
lock at the same four-hour expiry and eve's own inline-ownership lease at the same 860s/900s-max
shape as before this bump — nothing in the vendored source moved. The two anomalies seen during
this slice's proof runs (above) were both fast, explicit errors, never a timeout, and both cleared
on immediate retry — neither looks like LAR-73's intermittent 120-second `subprocess` timeout, but
they are data points for whoever is chasing that ticket, particularly the Docker-contention one
(evidence: another project's Postgres test containers sitting in `Created` state on the same
machine at the moment of failure).

## Proving it again after the next bump

CI wiring for these proofs (a Docker-in-Docker job running the two Postgres-backed probes below) is
**left as an owner decision** — not built in this slice. Until then, run these by hand after any
eve or `@workflow/world-postgres` version change, in this order (each needs Docker; check `uptime`
first and keep at most one heavy run going):

```bash
# 1. The restart proof — a genuine process boundary, tool-approval survives it, exactly once.
bash packages/board-evals/scripts/restart-probe.sh
# expect: RESTART PROOF PASS: authored control + definition catalogue.

# 2. The conversation-runtime probe — session-pinned model alias, definition edits, session reset.
pnpm -C services/keeper exec tsx tests/conversation-runtime.probe.mts
# expect: PASS: session-pinned direct provider aliases, new-session model edit, ...

# 3. The AFTER-vs-BEFORE tool/instruction gate for all three roles (~2.5 min, real `eve invoke`).
pnpm -C packages/board-evals run snapshot:compare
# expect: "tools-<role>.txt unchanged" and "instructions-<role>.txt unchanged" for chief-of-staff,
# travel and creative; a system-prompt diff is printed but never fails this gate — cross-check any
# new line against snapshots/system-prompt-allowlist.md.

# 4. The workflow-schema upgrade path (old shape -> upgrade file -> new shape, idempotent, and
#    fresh-install still works) — re-run whenever @workflow/world-postgres moves again.
pnpm -C services/chief-of-staff exec vitest run tests/eve-workflow-upgrade.test.ts
# expect: 4/4 passing (old+rows -> upgrade -> new; upgrade twice; fresh -> upgrade -> new; new -> upgrade).
```

A version bump that changes which `@workflow/world-postgres` beta pairs with the new eve also needs
a fresh regenerated `services/{chief-of-staff,creative}/sql/001-eve-workflow.sql`
(`pnpm -C services/chief-of-staff run regen:eve-sql:check`) and, if the schema shape changed again,
a new upgrade file alongside it, proven the same way as `006-eve-workflow-beta32-to-beta42-upgrade.sql`
was.
